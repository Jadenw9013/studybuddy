# Live Tutor stack audit and revised Codex prompt

Decision date: November 16, 2026. This is an addendum to the greenfield handoff. It covers the high-impact choices in the architecture and the three suggested developer skills. It adds early engineering experiments. The transfer-learning, privacy, and release criteria in the handoff still apply.

## Decisions before development

1. Keep Playwright Test for repeatable end-to-end tests. Make the Playwright CLI skill optional for interactive development. The production tutor sends named actions directly to its board or the paired notebook. No browser automation package is required for a student to see a chart.
2. Treat Gemini Live and the audio relay as separate decisions. Test live audio, tool calls, interruption and cost in M0. Build only one production voice path.
3. Keep the course stack consolidated on Postgres. Test whether semantic search improves citation quality enough to earn its indexing cost. Keep the stable interfaces so this experiment does not require changing the product.
4. Use a structured local renderer for numbers, equations and highlights. Measure time to the first correct board update from the student's perspective. An illustration model is optional after the pilot.
5. Test with actual coursework before changing PDF parsers. A faster contender won a synthetic text-only comparison below. The evidence does not cover the lecture figures and equations where a bad extraction would matter most.

## What was actually measured

A 60-page, 41,081-byte, generated statistics lecture contained one header, 15 short examples, and a footer per page. The input stayed in memory. After one warm-up per parser, a seeded random order determined which ran first in each of 20 pairs, on the same worker. Timing covered opening the PDF and extracting all page text. Every timed result matched all 1,020 expected lines after whitespace normalization, on the correct pages.

| Extractor | Warm median | Warm p95 | Timed documents |
|---|---:|---:|---:|
| pypdf 6.21.4 | 88.6 ms | 97.2 ms | 20 |
| pypdfium2 5.13.0 | 16.2 ms | 17.0 ms | 20 |

PDFium was about 5.5× faster here, saving about 72 ms per synthetic document. Real reading order, glyph fidelity, memory on large files, scans, embedding time and network transfer were outside this test. The faster option is worth retaining as a candidate. The result does not justify changing the default for this pilot by itself.

A local Playwright/Chromium timing attempt stopped at browser startup because this execution environment denied a required socket. No browser timings were collected. No paid live-provider sessions, production chart timings or head-to-head voice tests were performed for this audit. The source links document capabilities rather than an independently measured speed ranking.

## The decision that can change the business

Google documents that Gemini Live bills the active history again on subsequent turns, including retained audio. Transcription can add billed text output. A 20-minute lesson with lots of short corrections can therefore cost differently from a 20-minute monologue. Keep durable lesson state and relevant excerpts in the app. Budget the live context separately and test what the tutor still recalls after compression. [Google Live billing and context compression](https://ai.google.dev/gemini-api/docs/live-api/best-practices#pricing-billing), [pricing](https://ai.google.dev/gemini-api/docs/pricing)

At $19 per pass, the proposed $7.60 variable-cost ceiling allows **9.5 cents per included live minute at full use before allocating anything to chat, payment processing, ingestion or infrastructure**. During M0, run a real 20-minute lesson with interruptions, screenshots and a reconnect. Log provider-reported usage per turn, the context policy, minutes, frame count, and per-pass projection. Reconcile against billing when available. M0 is an early warning. Keep the bigger acceptance samples and real-device checks from the release plan.

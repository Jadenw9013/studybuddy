# Storage and ingestion implementation

The verified handoff remains unchanged. The API serializes each learner's transaction through a locked `learner_state` JSONB aggregate, validates course and source membership, fences asynchronous work by version and lease token, increments its revision, and commits before broadcasting. Migration 003 and the transactional domain projector maintain normalized profiles, entitlements, courses, sources, versions, datasets, jobs, lessons, messages, boards, actions, attempts, grants, usage, and payment records alongside that aggregate. Composite foreign keys constrain owner/course/source/version relationships, including the retrieval index. The per-owner row lock provides the pilot's concurrency boundary; normalized tables enforce domain relationships independently.

The migration creates a dedicated `tutor_api` NOLOGIN, NOBYPASSRLS role. The API must `SET LOCAL ROLE tutor_api`, set the authenticated subject for that transaction, and use only the trusted server database connection. Browser `anon` and `authenticated` roles have no privileges on the aggregate, preventing a direct PostgREST update from changing entitlements or action receipts. The owner primary key is indexed and references `auth.users`. The API's configured login must be allowed to set `tutor_api`; local `postgres` receives this membership in the migration. Never expose that database credential to a browser.

`course-originals` is private. A restrictive storage policy denies direct `anon` and `authenticated` operations on that bucket, even if another permissive policy exists. Server storage credentials retrieve bytes only after the application checks the current owner/course/source tombstone; ordinary previews use the authenticated source-content API and byte ranges. No signed bearer download links are generated. Original objects use owner/course/source/version paths. The real local Supabase service probe verified private uploads, JWT direct-download denial, authenticated ranges, and revocation after deletion using synthetic files. Hosted deployment and external-mailbox checks remain separate.

The Python worker is separate from the API and voice relay. It authenticates with `INTERNAL_WORKER_SECRET`, claims through `POST /internal/jobs/claim`, parses in a subprocess with a 45-second timeout, then publishes with the same job ID and lease token through `POST /internal/jobs/publish`. It reads local fixture bytes or downloads through the authenticated internal API. The API owns the durable lease, retry count, source-version/tombstone check, and atomic publication. A timed-out or stale parse cannot publish under a different token. A parse failure receives a visible status rather than a fabricated source. Worker responses contain data only.

Set `API_INTERNAL_ORIGIN` to the internal API origin (development default `http://127.0.0.1:3001`). Set `INTERNAL_WORKER_SECRET` consistently in both processes. The development default is `local-worker-development-secret`; production startup refuses that default. The internal endpoints must be private to the deployment network in addition to requiring the secret.

The parser accepts selectable-text PDF (200-page cap), UTF-8 CSV (100,000 rows and 100 named columns), notebook v4, and plain text. Every file is capped at 25 MB. It preserves physical PDF page indices, stable cell IDs and source hashes, CSV row intervals, quoted commas and quoted newlines. Formula strings remain strings; notebooks are never executed and active outputs are excluded. No external resource is fetched. PDFs without extractable text produce `needs_attention` and skipped-page evidence. Text is chunked within one page/cell. The current extraction stores normalized whitespace for retrieval; exact original bytes remain available in private previews. Bounding-box highlighting is not claimed.

Python is pinned to 3.12.12 and dependencies are locked in `apps/worker/uv.lock`. Development installed the environment at the repository's `.venv`. On PowerShell:

```powershell
$env:UV_PROJECT_ENVIRONMENT = "$PWD\.venv"
uv sync --project apps/worker --python 3.12.12 --frozen
.venv/Scripts/python.exe scripts/generate-fixtures.py
.venv/Scripts/python.exe apps/worker/runner.py
```

Original synthetic fixtures are generated both at `fixtures/` and `fixtures/demo/`. `fixtures/unseen/` has a distinct twelve-row dataset and renamed filenames for the second upload journey. `fixtures/decoys/` contains quoted CSV, a no-text PDF, untrusted instruction text, and probability/regression data. No real student files or identities are bundled. Their generated SHA-256 values live in `fixtures/manifest.json`.

Observed verification in this environment: Python 3.12.12; nine parser tests passed, covering exact page 2, all ten CSV rows, quoted multiline CSV/formula preservation, stable notebook IDs/active-output removal, deterministic fallback IDs for older notebooks, no-text PDF, malformed CSV rejection, nonfinite/missing accounting, and disguised PDF rejection. The generator ran and the parser returned the expected page-2 density definition and ten exact score rows. Run `python apps/worker/test_parser.py` using the project environment. Real local Postgres owner-RLS, scoped lexical/vector queries, direct browser-role privilege denials and normalized domain constraints passed. The **9/9** local Supabase service report at `evals/results/supabase-service.json` records real code/session, ordinary uploads and worker publication, exact page/range, normalized board/provenance, independent first response versus assisted retry, duplicate-action deduplication, direct storage denial, unavailable provider, delete/range revocation and account purge. These local synthetic checks do not establish live tutoring-provider or paid-pilot success.

## Indexed and optional semantic retrieval

The second migration creates `retrieval_passages` with exact text, JSON locator, FTS `tsvector`, optional `vector(384)`, owner RLS, scope B-tree indexes, and a GIN text-search index. Publication must use `indexPassages` in the same locked transaction as the current source/lease check. Deletion invalidates index rows in the same transaction as source revocation. Queries filter owner, course, and an explicitly supplied set of allowed current versions before either ranking. Natural questions become bounded OR terms for recall; the original request stays unchanged in the tutor prompt. RRF fuses up to ten lexical and ten semantic results with k=60, returning at most four passages. The pilot uses exact scoped cosine ranking; an approximate vector index requires a measured scale problem first.

`apps/worker/embeddings.py` pins `BAAI/bge-small-en-v1.5` to revision `5c38ec7c405ec4b44b94cc5a9bb96e735b38267a`, verified against the model's primary Hugging Face Git HEAD. The adapter checks the actual model/tokenizer limit including special tokens, splits without silently truncating, retains page/cell/row and character locators, and validates normalized 384-dimensional results. It adds the model-card query instruction only to queries. Remote model code is disabled. Normal calls load local cached weights only; a missing optional dependency or cache yields an explicit failure. A job/version namespace distinguishes identical passages in different courses. Model changes require re-indexing, and semantic SQL filters the pinned revision.

Optional CPU dependencies are pinned in the `embeddings` extra and locked. The development environment has prepared the pinned weights in `.data/model-cache`. To prepare deliberately on another machine:

```powershell
$env:UV_PROJECT_ENVIRONMENT = "$PWD\.venv"
uv sync --project apps/worker --python 3.12.12 --extra embeddings --frozen
.venv/Scripts/python.exe apps/worker/embeddings.py --prepare
```

Five TypeScript ranking/scoping/vector-validation tests and three synthetic-tokenizer contract tests passed. They verify implementation behavior, not retrieval quality. `node --import tsx supabase/tests/retrieval-live.ts` runs actual pinned BGE inference and local Postgres ranking on twelve developer-authored synthetic questions, recording lexical/hybrid recall, indexing/query timings, and wrong-course/stale/other-owner denials in `evals/results/retrieval.json`. It includes genuine PDF, notebook, and CSV extraction locators and supplemental original probability/regression notes. Every fixture database row is rolled back. A blinded lexical-versus-hybrid comparison on instructor-reviewed questions remains open; the small engineering probe cannot establish a semantic-quality improvement for learner coursework. [Primary BGE model card](https://huggingface.co/BAAI/bge-small-en-v1.5) and [Sentence Transformers implementation](https://github.com/huggingface/sentence-transformers) informed the adapter.

Observed comparison on Windows x64, Node 22.16.0 and local Postgres 17.11: eight synthetic documents, fifteen indexed passages, twelve developer-authored questions. Lexical recall@4 was 12/12 and hybrid recall@4 was 12/12. No stale/wrong-course/other-owner passage appeared in 24 ranked result sets; an additional cross-owner request returned zero rows (0/1 disclosures). Five repeated indexing passes had median 17.34 ms and p95 18.39 ms. Lexical SQL retrieval had median 0.88 ms and p95 2.06 ms over twelve queries; hybrid SQL retrieval had median 1.90 ms and p95 7.98 ms over twelve queries. The document embedding batch took 10.27 seconds and the twelve-query embedding batch took 5.15 seconds, each including cold Python/model process startup. SQL timings exclude those embedding batches, provider inference, WAN, audio and painting. This small set showed no recall gain from enabling hybrid search, so lexical-only remains the default pending reviewed evidence. These measurements do not close the release grounding or end-user latency gates.
